1. Project Objective

Build a production-grade CDC Data Lake Pipeline for an e-commerce platform that continuously captures changes from an OLTP database and makes the data available for analytics.

The system MUST handle:

Workload variety

  • Normal transaction volumes
  • Sudden festival/promotional spikes
  • INSERT, UPDATE, DELETE operations
  • Duplicate & out-of-order events

Resilience & ops

  • Schema evolution
  • Processing failures
  • Data-quality failures
  • Replay & recovery
  • Monitoring & alerting
Design goals: reliability, scalability, fault tolerance, security, observability, maintainability.

2. Business Scenario & SLA

Source system is an e-commerce application. On normal days transaction volume is manageable. During Diwali, big sales, flash sales, promotional campaigns, volume can spike sharply within a short period. The architecture MUST absorb bursty workloads without losing data.

Initial target SLA

CDC changes should become available in the analytical Silver layer within ~15 minutes under normal operating conditions, while the system remains capable of absorbing temporary traffic spikes.

The pipeline MUST handle sudden increases in CDC traffic.

ConditionApprox volume
Normal5,000 events/min
Festival100,000 events/min

The architecture must not assume the processing layer can always keep pace with arrival rate.

Kinesis as buffer

DMS→ Kinesis→S3 / Processing
Critical: temporary processing slowdown must not result in data loss. The system should monitor consumer lag and scale processing appropriately.

7. Silver Layer

Apache Iceberg — Silver represents the current state of the source.

101 → INSERT → PLACED
101 → UPDATE → SHIPPED
101 → UPDATE → DELIVERED
------------------------------
Silver:   101 | DELIVERED

Required operations: INSERT, UPDATE, DELETE, MERGE.

Iceberg MUST provide: ACID transactions, snapshot management, schema evolution, time travel, reliable MERGE operations.

8. CDC Ordering

The pipeline MUST correctly handle multiple changes to the same record.

PLACED→ SHIPPED→DELIVERED

If events arrive out of order, source transaction / LSN / commit-timestamp metadata must be used to determine the correct sequence. An older event must never overwrite a newer state.

9. Idempotency

Processing MUST be idempotent. If the same CDC event is processed twice, the target must not become corrupted or contain unintended duplicates.

Maintain suitable: event/source identifier, source position, transaction metadata, and processing metadata for deduplication.

10. DELETE Handling

DELETE events MUST be explicitly handled. The corresponding current-state Silver record must be removed according to the defined retention/business rules. Deletes must not silently disappear during transformation.

11. Data Quality

The pipeline MUST perform automated data-quality checks.

order_id      IS NOT NULL
customer_id  IS NOT NULL
order_amount >= 0
status IN ('PLACED','SHIPPED','DELIVERED','CANCELLED')

Checks should cover: null mandatory fields, invalid data types, duplicate records, invalid status values, invalid timestamps, invalid CDC operations, and referential/business-rule violations where applicable.

12. Reject / Quarantine Layer

Invalid records should not necessarily stop the complete pipeline. Use S3 Reject.

s3://cdc-lake/reject/

Each rejected record MUST contain: original_event, error_reason, table_name, processing_time, batch_id.

13. Schema Evolution

The pipeline MUST detect and handle source schema changes (e.g. new column coupon_code added). Additive changes support controlled evolution.

Breaking changes

detect→ stop affected processing→ record error→send notification

Incompatible type changes must be detected and halted rather than silently corrupting data.

14. Orchestration

Amazon EventBridge + AWS Step Functions

EventBridge→ Step Functions→ Check input→ Process CDC→ Validate→ Deduplicate→ Apply CDC→ Update Iceberg→ Data Quality→ Gold Processing→ Audit→ SUCCESS

Step Functions must manage: workflow orchestration, retries, timeout handling, conditional branches, failure handling, job dependencies, execution status.

15. Retry Strategy

Transient failures SHOULD automatically retry with backoff.

Glue failure→ Retry #1→ Retry #2→ Retry #3→ Still failed→ SNS Alert

Retries remain safe because downstream processing is idempotent.

16. Failure Recovery

The pipeline MUST recover from: Glue failures, network failures, temporary AWS service failures, invalid records, processing timeouts, schema changes, downstream failures.

A failed pipeline must be restartable without manually fixing the target tables.

17. Replayability

Bronze data MUST allow downstream reconstruction.

Silver corrupted→ Read historical Bronze→ Reprocess→Rebuild Silver

Support: full replay, date-based replay, partition replay, batch replay, failed-batch replay.

26. Scalability

The system SHOULD scale independently at different stages.

CDC ingestion→ Kinesis→ Processing→S3/Iceberg

Peak traffic should not require permanently running maximum compute. Allow: Kinesis shard scaling, parallel processing, partition-based processing, Spark worker scaling, independent downstream scaling.

27. Performance Requirements

Track and optimize: CDC ingestion throughput, Kinesis lag, S3 write throughput, Glue processing duration, Iceberg MERGE performance, Athena query performance.

Partitioning and file sizes should avoid excessive small files. Iceberg maintenance should include compaction, snapshot cleanup, orphan-file cleanup according to retention policy.

28. Cost Requirements

Avoid

  • Unnecessary always-on compute
  • Excessive Kinesis capacity
  • Excessive CloudWatch log retention
  • Uncontrolled S3 storage growth
  • Excessive Athena scans

Use appropriate

  • S3 lifecycle policies
  • Iceberg maintenance
  • CloudWatch retention
  • Kinesis capacity planning
  • Glue job sizing
